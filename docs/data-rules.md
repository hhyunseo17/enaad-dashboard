# 매출 분류 대원칙 (data-rules)

> 이 문서는 `reviewer` 에이전트의 검증 기준이자, 데이터 로직 수정 시의 근거다.
> 모든 규칙은 실제 운영 데이터에서 검증된 값이며, 임의로 바꾸지 말 것.

## 1. 본부매출 기준
- 컬럼 `본부매출여부`가 `본부매출`인 행만 매출로 집계.
- 모든 집계 함수는 예외 없이 이 필터를 통과해야 한다.

## 2. 매출기준 (취급고 / 회계)
- 컬럼 `매출기준`: `실적` 또는 `회계조정`.
- **취급고 모드**: `실적`만 합산.
- **회계 모드**: `실적` + `회계조정` 합산.
- 프론트 전역변수 `revenueBasisMode`('performance' | 'accounting')로 분기.

## 3. 대분류 재분류 (5종 고정)
최종 대분류는 아래 5종만 존재한다. (재분류 로직은 `data-loader.js`)
- 일반광고
- IMC
- 인포머셜
- 큐톤광고 — 중분류 `skylife큐톤` 포함
- 기타광고 — 어드레서블 / 콘텐츠편성 / 기타광고 / 대행수익 등을 통합

주의: **어드레서블은 별도 대분류가 아니다.** 기타광고로 통합.

검증 기준 (참고 분포, 2025 기준):
- 일반광고 ~20,142 / 기타광고 ~2,985 / 인포머셜 ~1,651 / IMC ~1,020 / 큐톤광고 ~259

## 4. 매출 미인식 항목
- **대행수익**: 원칙적으로 매출 미인식. 단 중분류 `skylife큐톤`(약 39건)만 큐톤광고로 인정.
- **교환광고**(약 586건): 전부 매출 미인식.

## 5. applyFilters() / makeCommonMatch() (필터 로직의 단일 지점)
- **전역 `filteredData` 산출**: `js/core/filters.js`의 `applyFilters()`. 본부매출 여부, 매출기준(취급고/회계) 모드, 연/월, 부서/채널/방송·디지털/대분류 선택 필터, 대행사/광고주 검색어를 모두 검사.
- **개별 기능의 전월/전년 비교 등 커스텀 조합**(연/월·대분류 필터를 제외한 나머지 조건만 필요한 경우): `js/features/shared-helpers.js`의 `makeCommonMatch(eligibilityFn)`. 본부매출/매출기준/부서/채널/방송구분/대행사·광고주 검색어까지는 `applyFilters()`와 동일 조건을 재사용하고, 마지막 대상범위 조건(`isAdvMetricEligible` 또는 일반광고/IMC 한정 등)만 호출부가 주입한다. `js/features/mom.js`, `agency-comp.js`, `new-advertiser.js`가 사용.

**새 compute 함수는 이 두 함수 중 하나를 재사용한다.** 필터 로직을 복붙해서 우회하지 말 것 — 과거 동일 로직이 3개 파일에 개별 `commonMatch`로 중복 구현돼 있었고, 규칙 변경 시마다 일부만 반영되는 버그를 유발했다(현재는 `makeCommonMatch()`로 통합됨).

## 6. K2그룹 등 중복 계약 병합 (업프론트)
- 광고주(업프론트용) + 계약기간 기준으로 계약을 묶는다. 대행사가 여러 개여도 1개 계약.
- **`업프론트 비고`(`upfrontRemark`)가 있으면 광고주(업프론트용) 대신 이것을 그룹핑 키로 우선 사용**한다. K2그룹/롯데칠성/동원그룹/고혼진리퍼블릭 등 대부분의 합산 케이스는 `광고주(업프론트용)`이 이미 통일돼 있어 문제없지만, **DB손해보험/DB금융네트워크**처럼 동일 계약인데 `광고주(업프론트용)` 표기가 행마다 다른(`'DB금융네트워크'` vs `'DB손해보험'`) 경우가 있다. 이런 케이스는 `업프론트 비고`(`'DB손해보험, DB금융네트워크 합산'`)가 같은 딜임을 알려주므로 이를 키로 사용해 병합한다. 비고가 없으면 기존처럼 `광고주(업프론트용)`을 키로 사용.
- **같은 그룹키 + 같은 계약금액이 겹치는 기간으로 여러 번 등재된 경우 병합**한다(계약 갱신/재기재로 인한 중복). 예: K2그룹 2025년 8억원이 1~12월/3~12월로 두 번 → 하나로.
- 동원그룹+동원F&B는 원본에 이미 `동원그룹+동원F&B` 단일 광고주로 통합되어 있음(2.5억).
- 이 병합은 **data-loader에서만** 수행. UI에서 재구현 금지. `js/features/upfront.js`의 실적 피벗(실제 매출 `r.amount` 집계)은 이 병합과 무관하게 행 단위 `advertiser`/`upfrontAdvertiser` 원본 표기를 그대로 유지한다(예: DB손해보험/DB금융네트워크는 실적 피벗에서는 별도 라인으로 남는다 — 실제 매출 라인이 분리돼 있는 게 맞기 때문).

## 7. 업프론트 계약금액 (근사치)
- **`업프론트 계약금액` 컬럼은 순수 숫자(억원 단위)**다. 과거에는 "8억원(Net 5억원)" 같은 텍스트에서 정규식으로 GROSS/NET 두 금액을 함께 추출했으나, 현재 원본 데이터는 그런 텍스트 포맷을 쓰지 않는다.
- `GROSS/NET` 컬럼(`null`/`'GROSS'`/`'NET'`)은 그 숫자 하나가 어떤 기준액인지 나타내는 **라벨**일 뿐이다. `null`이면 GROSS로 취급(명시적 NET 표기가 없으면 기본 GROSS). 계약 목표금액(`targetWon`)은 `계약금액(억원) × 1e8`을 그대로 쓰며, 더 이상 GROSS/NET 두 금액 중 하나를 선택하는 로직이 없다.
- **월할 계산**: 계약기간을 월 단위 전개, 선택된 연/월과 겹치는 개월수 ÷ 전체 개월수를 곱함.
- **연걸침 계약은 정확 재현 불가**(팀 수기 배분). KPI에는 "약 XX.XX억원(월할 추정치)"로 표기.

## 9. 금액 표기 규칙
- 피벗 테이블: **백만원 단위, 소수 1자리**. 기본 접힘.
- 차트/KPI: **억원 단위**.
- 부서 정렬: 매출순이 아니라 커스텀 순서(광고사업1팀 → 2팀 → 3팀 → 공공비즈팀 → 뉴미디어광고팀 → 디지털영업팀 → 그 외 알파벳순 → 광고전략팀 → 광고사업본부). `state.js`의 `customDeptOrder`/`customDeptTailOrder` + `shared-helpers.js`의 `compareDeptOrder()` 단일 지점(6개 파일이 공유 — 복붙 금지).

## 10. skylife큐톤 담당자 재배분 (정확한 비율 규칙 — 근사치 아님)
- 원본 데이터는 중분류 `skylife큐톤`(4번 항목의 매출 미인식 예외 대상)인 행 전액이 원본 담당자 컬럼상 **박영상** 한 명에게 잡혀 있으나, 실제로는 여러 담당자가 나눠 갖는 구조다. 담당자별 집계(피벗/랭킹/목표KPI 등 담당자 필드를 쓰는 모든 화면)가 정확하도록 아래 비율로 **1행을 N행으로 분할**해 담당자·금액만 재배분한다.
- **적용 범위**: `중분류(sub_category) = 'skylife큐톤'`인 행만. 대분류 `일반광고`에도 존재하는 동명 소분류(`장초수`/`인포결합`)는 절대 대상이 아니다.
- **부서는 원본 행의 부서를 그대로 유지**한다(담당자만 바뀌고 부서는 안 바뀜 — 재배분된 남형진/김기철/이신우 조각도 원래 행의 부서로 표기).
- **금액은 비율이 아니라 나머지(remainder) 방식으로 분배**한다(마지막 조각 = 원금 − 앞 조각들의 반올림 합) — 조각별 독립 반올림 시 발생할 수 있는 원 단위 누적 오차 없이 SUM(amount_won)이 재배분 전후 항상 정확히 보존된다.
- **비율표**(2025/2026년만 규칙 존재, 그 외 연도는 재배분 없음 — 원본 담당자 그대로):

| 연도 | 소분류 | 담당자 | 비율 |
|---|---|---|---|
| 2025년 전체(1~12월) | `LiveAD+`, `심포니`, `영업대행수수료` | 박영상 / 남형진 | 50% / 50% |
| 2025년 전체(1~12월) | `장초수`, `인포결합` | 박영상 / 김기철 | 65% / 35% |
| 2025년 전체(1~12월) | 그 외 소분류 | 재배분 없음(원본 담당자 유지) | - |
| 2026년 1~4월 | 소분류 무관 | 박영상 / 남형진 | 50% / 50% |
| 2026년 5~12월 | 소분류 무관 | 박영상 / 남형진 / 이신우 | 50% / 30% / 20% |
| 2023·2024·2027년 등 (2025/2026 외) | 소분류 무관 | 재배분 없음(원본 담당자 유지) | - |

- **구현 위치**: Supabase 경로는 `supabase/schema.sql`의 `v_manager_split`(규칙별 `UNION ALL` 브랜치 — 복합타입+`unnest` 방식은 SQL Editor에서 CASE 분기 간 배열 타입 통일이 깨지는 문제를 실제로 겪어서 포기하고, 브랜치별 `SELECT`를 나열하는 더 단순한 방식으로 구현) → `v_sales_normalized`가 `raw_sales_rows`와 `v_manager_split`을 `raw_id`로 조인해 1행→N행 확장을 반영. xlsx 안전망 경로는 `js/core/data-loader.js`의 `getManagerSplitParts()`(`processWorkbookBuffer()` 내부, `finalizeLoadedData()` 호출 전). **두 경로 모두 동일 규칙을 유지해야 한다** — 한쪽만 고치면 xlsx 롤백 시(`DATA_SOURCE_MODE='xlsx'`) 재배분이 사라진다.
- **id 처리(Supabase)**: `v_sales_normalized`/`v_bonbu_sales`의 `id`는 `raw_sales_rows.id * 100 + split_idx`(1-based)로 합성한다 — 분할로 한 raw 행이 여러 행이 되면서 `id`가 중복되는 것을 방지. 최대 3분할이므로 100이면 여유 있음. 원본 raw 행은 `raw_id` 컬럼으로 추적 가능.
- **검증 시점(2025년, 2026-08 데이터 기준)**: 2025년 skylife큐톤 본부매출 166건 전부 위 5개 소분류(`LiveAD+`/`심포니`/`영업대행수수료`/`장초수`/`인포결합`) 안에 들어와 있었다(규칙 미정의 소분류 0건). 2026년은 8월까지 111건. 데이터가 갱신되며 새 소분류가 추가될 수 있으니, ETL 재적재 시 규칙 밖 소분류가 새로 생기지 않았는지 주기적으로 확인할 것.
